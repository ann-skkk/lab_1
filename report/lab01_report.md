# Отчёт: Лабораторная работа №1

## Цель работы

Разработать пайплайн интеллектуального интерфейса к каталогу товаров. LLM интерпретирует естественный язык и возвращает проверяемые параметры поиска; Python валидирует их и выполняет поиск по SQLite. Модель не формирует и не исполняет SQL.

## Архитектура

`Пользователь → ChatPromptTemplate → ChatOpenAI → PydanticOutputParser → ProductQuery → search_products → SQLite`.

Для вызова инструмента используется второй вариант: `bind_tools([search_products])`. Аргументы `tool_calls` ещё раз валидируются через `ProductQuery`, только после этого запускается SQL-поиск. Состояние диалога (`last_query`, история) хранится в объекте `Conversation` вне модели.

Токен считывается из `.env` через `python-dotenv`; в исходном коде, результатах и отчёте его нет.

## Часть 1. Базовая цепочка

`ChatPromptTemplate` содержит system-сообщение с ролью и human-сообщение с переменными `query` и `language`. Цепочка собрана оператором LCEL: `prompt | llm | StrOutputParser`.

Прямой вызов LLM вернул `AIMessage` (20 входных, 37 выходных токенов); после `StrOutputParser` результат имеет тип `str`. Метод `batch` обработал три запроса: «Нужен ноутбук» → «Ноутбуки», «Ищу смартфон» → «Смартфоны», «Хочу планшет» → «Планшеты».

## Часть 2. Structured Output

Схема `ProductQuery`:

| Поле | Тип | Ограничение |
|---|---|---|
| `category` | Literal | `laptop`, `smartphone`, `tablet`, `other` |
| `max_price` | `int \| None` | `>= 0` |
| `sort_by` | Literal | `price_asc`, `price_desc` |

`PydanticOutputParser.get_format_instructions()` включён в system prompt. Цепочка возвращает валидный Pydantic-объект, сериализуемый через `model_dump_json()`.

### Таблица проверок

| Запрос | Полученный JSON | Время, с | Проверка |
|---|---|---:|---|
| Найди ноутбуки дешевле 70 000 рублей | `laptop`, 70000, `price_asc` | 0,448 | успешно |
| Покажи самые дорогие смартфоны | `smartphone`, null, `price_desc` | 0,373 | успешно |
| Хочу посмотреть планшеты | `tablet`, null, `price_asc` | 0,351 | успешно |
| Покажи ноутбуки до 50 тысяч | `laptop`, 50000, `price_asc` | 0,404 | успешно |
| Найди холодильники | `other`, null, `price_asc` | 0,407 | успешно |
| Покажи недорогие ноутбуки | `laptop`, null, `price_asc` | 0,412 | цена не задана явно |
| А сначала дорогие? | `other`, null, `price_desc` | 0,409 | без контекста категория не определена |

### Режим размышления

На двух неоднозначных запросах сравнивались `enable_thinking=False` и `True`. В обоих режимах парсер успешно разобрал `content`; в content находился только JSON (с Markdown-ограждением при выключенном thinking). Скрытое рассуждение не вошло в content, однако проявилось ростом числа выходных токенов и времени.

| Запрос | Thinking off: время / токены | Thinking on: время / токены | Параметры |
|---|---|---|---|
| Недорогие ноутбуки | 0,337 с / 36 output | 1,811 с / 193 output | `laptop`, null, asc |
| А сначала дорогие? | 0,510 с / 35 output | 2,866 с / 297 output | `other`, null, desc |

Таким образом, JSON-парсер должен получать только `content`, а рассуждение, если сервер хранит его отдельно, нельзя добавлять к разбираемой строке: это нарушит JSON-формат.

## Часть 3. SQLite и инструмент

Таблица `products` включает 15 товаров: по четыре ноутбука, смартфона и планшета и три аксессуара. `search_products` строит запрос только из фиксированных SQL-фрагментов; пользовательские значения передаются параметрами SQLite. Для `other` возвращается сообщение о неподдерживаемой категории, без поиска по всем товарам.

### Результаты объединённого пайплайна

| Запрос | Параметры | Найденные товары / результат | Корректность |
|---|---|---|---|
| Ноутбуки до 70 000 | laptop, 70000, asc | Acer Aspire 5; Lenovo IdeaPad Slim 3 | да |
| Самые дорогие смартфоны | smartphone, null, desc | 4 смартфона, iPhone 16 → Redmi Note 14 | да |
| Планшеты | tablet, null, asc | 4 планшета | да |
| Ноутбуки до 50 000 | laptop, 50000, asc | 0 товаров | да |
| Холодильники | other, null, asc | неподдерживаемая категория | да |
| Недорогие ноутбуки | laptop, null, asc | 4 ноутбука, без цены в запросе | ожидаемо |
| А сначала дорогие? | other, null, desc | неподдерживаемая категория без контекста | ожидаемо |
| Планшеты до 30 000 | tablet, 30000, asc | Samsung Galaxy Tab A9+ | да |
| Смартфоны до 20 000 | smartphone, 20000, asc | 0 товаров | да |
| Ноутбуки до 10 000 | laptop, 10000, asc | 0 товаров | да |

На тех же трёх вопросах без доступа к базе модель не стала выдумывать каталог: сообщила, что у неё нет доступа к внутреннему списку товаров, и предложила предоставить данные. Это подтверждает, что источником ответа о наличии является SQLite, а не LLM.

При `bind_tools` все пять обязательных запросов привели к вызову `search_products`, а `content` ответа был пустым и `finish_reason` равнялся `tool_calls`. Например, для ноутбуков до 70 000 модель передала `{"category":"laptop","max_price":70000,"sort_by":"price_asc"}`; после валидации функция вернула два товара. Для холодильников передан `category="other"`, после чего приложение вернуло статус неподдерживаемой категории. Для ответа без вызова инструмента получен статус `no_tool_call` и сообщение «Модель не вызвала инструмент поиска»; этот сценарий также проверен unit-тестом. В варианте parser JSON извлекается из `content` приложением; в варианте tool call сервер возвращает уже разобранный вызов, но проверка и действие всё равно остаются за приложением.

## Часть 4. Ошибки, retry и журнал

Проверены три ошибки:

| Некорректный ответ | Тип ошибки | Этап пайплайна |
|---|---|---|
| `{category: laptop}` | `OutputParserException` | синтаксический разбор JSON |
| `{"category":"camera"}` | ошибка `Literal` в Pydantic, завёрнутая парсером | валидация категории |
| `{"category":"laptop","max_price":-5}` | ошибка ограничения `ge=0`, завёрнутая парсером | валидация цены |

`with_retry` охватывает только генерацию и разбор, максимум три попытки; SQLite находится после этой границы.

Тесты с `FakeMessagesListChatModel` воспроизводят вариант без retry, невалидный JSON на первой и корректный JSON на второй попытке, а также три последовательные ошибки. `PipelineLog` хранит начало LLM-вызова, результат разбора, валидацию и запуск поиска. Фрагмент журнала сценария с успешной второй попыткой:

```text
[llm, attempt=1] Начало вызова LLM
[parse_error, attempt=1] OutputParserException: Invalid json output
[llm, attempt=2] Начало вызова LLM
[validation, attempt=2] {"category":"laptop","max_price":70000,"sort_by":"price_asc"}
[search] Найдено товаров: 2.
```

Без retry первый невалидный ответ сразу завершает цепочку ошибкой. С retry поиск отсутствует после первой неуспешной попытки и запускается только после успешной проверки параметров. При трёх ошибочных ответах цепочка заканчивается понятным исключением, а поиск не выполняется; это проверяется отдельным unit-тестом.

## Часть 5. Уточняющие запросы

Первый вариант передаёт предыдущий валидный `ProductQuery`, второй — всю историю. На двух диалогах оба варианта сформировали одинаковые параметры на всех шести репликах. Число входных токенов извлекается из `usage_metadata.input_tokens` ответа модели.

| Диалог, реплика | Параметры | Только состояние, токены | История, токены |
|---|---|---:|---:|
| Ноутбуки до 80 тыс. | laptop, 80000, asc | 355 | 350 |
| А сначала дорогие? | laptop, 80000, desc | 370 | 398 |
| Среди смартфонов | smartphone, null, asc | 373 | 448 |
| Хочу планшеты | tablet, null, asc | 350 | 345 |
| Только до 35 тыс. | tablet, 35000, asc | 367 | 391 |
| Теперь самые дорогие | tablet, 35000, desc | 368 | 437 |

На первой реплике разница определяется только формулировкой системного сообщения. Начиная со второй реплики передача только состояния требует меньше входных токенов; история остаётся полезной, когда новая реплика ссылается на более ранние детали диалога.

## Контрольные вопросы

1. В пайплайне порядок действий задан программой: сначала извлечение параметров, затем проверка и поиск. Агент сам выбирает, вызывать ли инструмент, какой именно и что делать с ответом.

2. Компоненты LangChain объединяются оператором `|`: результат предыдущего компонента передаётся следующему. `StrOutputParser` берёт текст из `AIMessage` и возвращает обычную строку.

3. System-сообщение задаёт постоянные правила и роль модели. Human-сообщение содержит конкретный запрос пользователя и переменные, которые меняются между вызовами.

4. Structured Output — это ответ с заранее известной схемой полей и типов. В произвольном текстовом ответе модель может добавить объяснения, изменить названия полей или вернуть данные в неудобном формате.

5. `BaseModel` задаёт модель данных и выполняет валидацию. `Field` добавляет ограничения, значения по умолчанию и описание. `Literal` ограничивает поле фиксированным набором допустимых значений.

6. Без доступа к каталогу модель не знает, какие именно товары и цены есть в базе. Она может назвать типичные модели, но не может гарантировать наличие или корректную стоимость.

7. При `PydanticOutputParser` приложение само разбирает JSON из `content`. При `bind_tools` сервер возвращает распознанный вызов в `tool_calls`. В обоих случаях приложение должно проверить аргументы и самостоятельно выполнить поиск.

8. Валидация не даёт передать в программу неизвестную категорию, отрицательную цену или другой неподходящий тип. SQL от модели нельзя исполнять напрямую: он может быть ошибочным, небезопасным или обращаться к данным вне поставленной задачи.

9. Retry нужен для ошибок формата и валидации ответа модели. Повторная генерация с тем же промптом просит модель ответить заново; исправление с учётом предыдущей ошибки добавляет в следующий промпт информацию о том, что именно было неверно.

10. Состояние хранится в программе: как минимум последний валидный `ProductQuery`, при необходимости — история реплик. В модель передаётся новая реплика вместе с выбранным представлением этого состояния.

## Выводы

В работе получился пайплайн, в котором модель отвечает только за интерпретацию текста. Проверка параметров, выбор SQL-конструкций, доступ к SQLite и хранение состояния остаются в обычном программном коде. Это делает поиск воспроизводимым и позволяет изолировать ошибки модели до обращения к каталогу.
